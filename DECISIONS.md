## Step 04 — full run performance fix (before any verdict existed)

- `semantic_knn`'s first full-run attempt used sklearn `NearestNeighbors(metric="cosine")` doing brute-force search against HDFS's ~335k-session training set. One cell (HDFS/random/seed0) took ~45 minutes (vs seconds for every other arm), which would have meant roughly 7.5 hours for HDFS's 10 semantic_knn cells alone -- a serious risk to the overall compute budget (PROTOCOL.md's compute-plan rule). Killed the run (only 21/124 cells were done; all preserved, `run_all.py` is resumable) and rewrote the arm to compute cosine distance as a batched, GPU matrix multiply (L2-normalise, dot product, `torch.topk`) instead of sklearn's brute force. This computes the exact same quantity -- mean cosine distance to the k=10 nearest training session embeddings -- just on a faster backend; it is a performance fix, not a methodology change, and no verdict existed yet.
- The fixed version's first fixed batch size (4096) was itself too large: the similarity-matrix tensor (batch x n_train_sessions) for HDFS (n_train ~335k) was 4096*335036*4 bytes ~= 5.11 GiB, which overflowed the 6 GB GPU (`torch.OutOfMemoryError`). Changed to a dynamic batch size that caps the similarity matrix at ~20M elements (~80MB) regardless of `n_train`, and added `torch.cuda.empty_cache()` after every cell in `run_all.py` as a defensive measure against cross-cell fragmentation. Re-validated on `--selftest`: identical AUPRC/AUROC numbers to the pre-fix run, confirming this is purely a memory-footprint fix. Resumed with `python src/run_all.py` (skips the 21 already-completed cells).
- All 120 non-LLM cells (2 datasets x 2 splits x 6 arms x 5 seeds) completed successfully. The `llm_zeroshot` arm then hit a `CUDA out of memory` loading the 1.5B model, even though the error itself reported 3.73 GiB free for a 28 MiB request -- GPU memory fragmentation after a long-running process cycled many CUDA tensors through dozens of prior cells, not a real capacity shortfall. Resumed `run_all.py` in a fresh process (clean CUDA context) with `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` set, as the error message itself suggested, rather than changing any arm's code.
- That retry OOM'd again at model load (2.59 GiB allocated, needed 28 MiB more) even in a fresh process, and `expandable_segments` logged as "not supported on this platform" (Windows) -- a no-op. `nvidia-smi` showed GPU memory usage fluctuating independently of our process (this machine's single GPU is also the Windows display adapter, shared with the desktop/browser/IDE), so the OOM is GPU contention with other running software, not a bug in our code or a real capacity problem. This was attempt 2 of the pre-registered protocol's "two attempts and one simplification" rule for marking an arm SKIPPED. As the one simplification, added a try/except around the GPU model load in `llm_zeroshot.py` that falls back to loading the same `Qwen2.5-1.5B-Instruct` model on CPU (fp32) if CUDA OOMs -- the model and sample size are unchanged, only the device. This is a one-time, sample-based (400 sessions/combo, seed 0 only) exploratory arm reported separately from the main ranking table, so a CPU fallback's slower runtime does not threaten the 14-hour budget materially.
- The multi-candidate fallback (1.5B GPU -> 0.5B GPU -> 0.5B CPU) was validated on `--selftest` (30-sample sets): the first combo succeeded by falling through to CPU, but took 1987s (~33 min) for just 30 generations (~66s/generation -- the dominant cost is the ~40-line prompt + generation itself, not dataset size, so a real 400-sample combo would scale to several hours). The very next combo then failed outright on `OSError: The paging file is too small`, even for the smallest (0.5B, CPU, fp32) candidate -- this machine's virtual-memory/pagefile ceiling, not something a smaller model or a code fix resolves. Between the two GPU attempts (contention from the shared display GPU) and this CPU attempt (pagefile), `llm_zeroshot` has now failed in four different ways across more than the "two attempts and one simplification" the protocol allows (Section 5.5 decision rules) before marking an arm SKIPPED. **Decision: `llm_zeroshot` is marked SKIPPED for the full run.** All 120 non-LLM cells (2 datasets x 2 splits x 6 arms x 5 seeds) completed successfully and are not affected -- H1-H5 as pre-registered depend only on `NON_LLM_ARMS`, so this skip does not touch any hypothesis. This is exactly the scenario Section 5.3 anticipated ("hardware permitting") and Section 5.5 explicitly allows for.

## Step 05 (written ahead, at implementation time — no analysis results exist yet)

- PROTOCOL.md says hypotheses H1/H4/H5 need "the 95% CI [of a difference] excluding zero," but Section 5.4 only defines a bootstrap CI for a single AUPRC estimate (resampling test sessions within one split condition). A CI for a *difference across split conditions* isn't directly given by two single-condition CIs. Decision: for H1 (AUPRC_random - AUPRC_chrono), H4 (difference of drops) and H5 (F1_oracle - F1_val gap), compute the CI by bootstrap-resampling the 5 per-seed values (with replacement, 1000 resamples, seed 0) and taking the 2.5/97.5 percentiles of the resampled mean. This uses the same 5 seeds the protocol already designates for reproducibility (Section 5.4 "across-seed standard deviation"), rather than inventing a new resampling unit. This is a methodology clarification made before any result exists, not a change made to move a verdict.
