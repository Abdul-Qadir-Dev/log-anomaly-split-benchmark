# Decisions log

A running log of the choices made during this project, with reasons, in the order they were made. Entries are not edited after a verdict is written (PROTOCOL.md Section 5); later changes get a new entry.

## Step 00: environment

- Python 3.11.9 (`py -3.11`).
- Hardware: NVIDIA GeForce GTX 1660 Ti with 6144 MiB VRAM, 12 logical CPUs, about 19.85 GB RAM (`results/hardware.json`). This is exactly the 6 GiB boundary of the protocol's GPU-present tier, so that tier was used: arms as specified, LLM arm with `Qwen2.5-1.5B-Instruct` in fp16, with a fallback to `Qwen2.5-0.5B-Instruct` to be recorded here if VRAM pressure caused failures.
- PyTorch installed as the CUDA build from `https://download.pytorch.org/whl/cu124`. The driver reports CUDA 13.1, which is backward compatible with the cu124 runtime bundled in the wheel.

## Step 01: data download

- HDFS_v1 downloaded and extracted cleanly from the primary Zenodo URL (186.6 MB zip, 1.58 GB `HDFS.log`), after two transient mid-download `IncompleteRead` drops that the streaming and resume logic in `scripts/download_data.py` recovered from with HTTP Range requests.
- BGL's first attempt exhausted all retries on both URLs because of a transient local DNS failure (`getaddrinfo failed` for zenodo.org) that lasted through the whole retry window. It was not a missing-file condition. BGL was retried on its own once DNS recovered.
- The BGL retry downloaded to 100% (57.5 MB, matching Content-Length), but the script's `MIN_SIZE_BYTES = 100MB` sanity floor assumed both archives would exceed 100 MB. BGL.zip compresses much better than HDFS_v1.zip, so a complete download was flagged as too small, which triggered pointless retries that then received HTTP 416 because the file was already whole. The zip was verified with `zipfile.testzip()` and extracted (`BGL.log`, 743 MB). The script now uses a 10 MB floor and treats a 416 on a resume attempt as "already complete". This was a bug in the download script, not a change to any result.
- `.gitignore` excludes `data/raw/*` with an exception for `data/raw/INVENTORY.md`, so the inspection notes (line counts, format notes, a few quoted lines) are tracked while the raw logs are not.

## Step 03: BGL parsing fix, before any verdict existed

- The first full BGL parse flagged 34,470 of 4,747,963 lines (0.73%) as unparseable. These turned out to be real log lines with an empty message field, for example `... RAS KERNEL FATAL` with nothing after the level field. `parse_bgl_line` used `split(maxsplit=9)` and required 10 tokens, so it rejected any line with only the nine fixed fields. It now accepts exactly nine fields with empty content and rejects only lines with fewer than nine. No verdict existed, so no `results/superseded/` entry was needed; BGL was re-parsed from scratch.

## Step 04: performance fix during the full run, before any verdict existed

- `semantic_knn`'s first full-run attempt used sklearn `NearestNeighbors(metric="cosine")`, a brute-force search against HDFS's roughly 335k-session training set. One cell (HDFS/random/seed0) took about 45 minutes against seconds for every other arm, which would have meant about 7.5 hours for HDFS's ten `semantic_knn` cells alone and put the compute budget at risk. The run was stopped (21 of 124 cells done, all kept; `run_all.py` is resumable) and the arm was rewritten to compute cosine distance as a batched GPU matrix multiply (L2-normalise, dot product, `torch.topk`). This computes the same quantity, the mean cosine distance to the k = 10 nearest training session embeddings, on a faster backend.
- The rewrite's first fixed batch size (4096) was too large: the similarity matrix for HDFS (4096 x 335,036 x 4 bytes, about 5.11 GiB) overflowed the 6 GB GPU. The batch size is now chosen dynamically to cap the matrix at about 20M elements (about 80 MB), and `run_all.py` calls `torch.cuda.empty_cache()` after every cell. Re-validated on `--selftest`: identical AUPRC and AUROC to the pre-fix version. The run was resumed and skipped the 21 completed cells.
- All 120 non-LLM cells (2 datasets x 2 splits x 6 arms x 5 seeds) completed. `llm_zeroshot` then hit `CUDA out of memory` while loading the 1.5B model even though the error reported 3.73 GiB free for a 28 MiB request, which points to fragmentation after a long process had cycled many tensors through dozens of cells. `run_all.py` was resumed in a fresh process with `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, as the error message suggests.
- That retry failed the same way at model load (2.59 GiB allocated, 28 MiB more needed), and `expandable_segments` logged itself as not supported on Windows. `nvidia-smi` showed GPU memory moving independently of this process: the single GPU is also the Windows display adapter and is shared with the desktop. This was attempt two under the protocol's "two attempts and one simplification" rule. As the simplification, `llm_zeroshot.py` got a try/except around the GPU model load that falls back to the same model on CPU in fp32, with model and sample size unchanged.
- The multi-candidate fallback (1.5B GPU, then 0.5B GPU, then 0.5B CPU) was checked on `--selftest` with 30-sample sets. The first combination succeeded by falling through to CPU but took 1987 seconds (about 33 minutes) for 30 generations, about 66 seconds each, so a real 400-sample combination would take several hours. The next combination failed outright with `OSError: The paging file is too small`, even for the smallest candidate (0.5B, CPU, fp32). This is the machine's virtual-memory ceiling, not something a smaller model or a code change resolves. Having failed in four different ways across more than the attempts the protocol allows, `llm_zeroshot` was marked SKIPPED for the full run. H1 to H5 depend only on the six non-LLM arms, which were unaffected.

## Step 05: CI for differences, written before any analysis result existed

- PROTOCOL.md requires "the 95% CI of a difference excluding zero" for H1, H4 and H5, but Section 5.4 defines a bootstrap CI only for a single AUPRC estimate within one split condition. Two single-condition CIs do not give a CI for the difference. Decision: for H1 (AUPRC_random minus AUPRC_chrono), H4 (difference of drops) and H5 (F1_oracle minus F1_val), bootstrap the five per-seed values with replacement, 1000 resamples, seed 0, and take the 2.5 and 97.5 percentiles of the resampled mean. This reuses the five seeds the protocol already designates rather than inventing a new resampling unit. It is a clarification made before any result existed, not a change made to move a verdict.

## Step 08: post-hoc verification of the main run

- BGL parse re-verified by re-reading all 4,747,963 raw lines through `parse_bgl_line`: zero dropped, 348,460 alert-labelled lines (7.34%), 1,346 templates (well under the 5,000 over-fragmentation flag; the top-20 table was produced anyway). The empty-content template has exactly 34,470 occurrences, the same count the Step 03 bug used to drop, which confirms that fix was complete. BGL/CHRONO/seed0 `unseen_template_rate` recomputed independently is 0.7746 per occurrence, matching the recorded value, and 0.7500 per unique template; the per-occurrence number is higher because unseen templates also recur more often per session in the chronological tail.
- `semantic_knn` GPU scorer compared with a re-implementation of the original sklearn scorer on 5,000 HDFS/CHRONO/seed0 query sessions: maximum absolute score difference 5.4e-7 against a bar of 1e-4. The Spearman correlation between the two score arrays was only 0.23, which looked alarming until the cause was found: most HDFS test sessions are template-identical to some training session, so both scorers give near-zero scores for most queries (only 19 distinct rounded values across 5,000 points) and float32 versus float64 rounding reorders that tied block. AUPRC on the subsample was 0.97793 (GPU) versus 0.97792 (CPU) and AUROC was identical at 0.99968.
- H4 and H5 diagnosis written to `results/audit/h4_h5_diagnosis.md`, no verdict changed. HDFS_v1's aggregate threshold-leakage gap (0.0606) is driven almost entirely by one arm, iforest (gap 0.348); every other arm on that dataset has a gap under 0.02.
- `llm_zeroshot` retried with `Qwen/Qwen2.5-0.5B-Instruct`, which is allowed because no verdict depends on this arm. All four dataset x split cells completed on the GPU; the smaller model's VRAM footprint (well under 2 GB) avoided the contention that stopped the 1.5B attempts. Results in `results/audit/llm_zeroshot/` and `results/audit/llm_table.md`, not part of the main ranking.
- A reproducibility test on a fresh clone found two real bugs: `requirements.txt` pinned `torch==2.6.0+cu124`, a build string that does not exist on PyPI, now re-pinned to `torch==2.6.0` (which PEP 440 matches against any local-version variant); and the `data/sample/` selftest fixtures were gitignored and never fetched by any script, now fetched by `scripts/download_sample_data.py` and documented in `REPRODUCE.md`. A third issue, a Windows `MAX_PATH` failure when installing from a deeply nested temporary path, was specific to where the test clone lived and is documented as a troubleshooting note. After the two fixes every `--selftest` script passed on a fresh clone and fresh venv.

## Step 09: interpretation checks

- Selftest contamination: `results/full/summary.csv`, `paper/tables.md` and all four figures were regenerated from the frozen per-seed JSONs and compared with the committed versions. All identical, apart from matplotlib's embedded `/CreationDate` timestamp in the PDFs, which were discarded rather than committed as a timestamp-only change. One latent bug was fixed anyway: `src/make_figures.py` hardcoded `figures/` as its output directory regardless of `--selftest`, unlike `run_all.py` and `analysis.py`. Nothing had been overwritten because the full-data run always followed any selftest run, but the next person running `--selftest` after a full run could have overwritten the committed figures. Selftest output now goes to `figures/selftest/`, which is gitignored. `scripts/make_tables.py` reads only `results/full/summary.csv` and was never at risk.
- Prevalence and AUROC addendum, built from `results/full/summary.csv` with no re-run. HDFS_v1's test-set prevalence differs about twofold between RANDOM and CHRONO (2.96% versus 1.46%) purely because of where the single chronological cut falls, while AUROC stays nearly flat for every HDFS_v1 arm even where AUPRC swings by 0.09 to 0.33. BGL's AUROC and AUPRC drops track each other closely. Incorporated into `paper/draft.md`.
- Drift-mechanism test (`results/audit/drift_mechanism/`): a fresh `semantic_knn` was fitted on the existing BGL/CHRONO/seed0 split rather than reading back the frozen scores, so the check is independent of the main run. The mechanism only partly explains `semantic_knn`'s below-chance BGL AUROC: within-class correlations are strong and in the predicted direction, but the between-class unseen-rate gap is too small to explain an AUROC below chance rather than near it. Reported as a partial explanation.
- Rolling-origin check: result files are named `cutoff50_HDFS_v1_pca.json` and similar (not starting with `seed`) so they can never be swept into a future `summary.csv` regeneration, which globs `seed*.json` under `results/full/`. This found a previously undocumented limitation: HDFS_v1's 60% chronological split is not representative of nearby cutoffs (pca AUPRC 0.485 at 50%, 0.920 at 60%, 0.994 at 70%, with `unseen_template_rate` at zero throughout, which rules out drift as the cause). BGL's result is stable across all three cutoffs. Stated as a limitation in the paper.
- Baseline sanity table: every literature-value cell is marked n/a. We did not have a verified source for exact published figures for DeepLog and PCA on HDFS and preferred n/a with a citation and qualitative reasoning over an unverified number in a results file. The table states that our deeplog HDFS_v1 result is well below DeepLog's usual reported performance, with the 100k-window, 5-epoch training cap given as the likely cause at the time (Step 11 later found a larger cause).
- Paper reframing: the headline became "split inflation is dataset-dependent and tracks template drift"; a paragraph on the HDFS_v1 negative drops with the prevalence evidence was added; H3 was reworded to "consistent with" with the effective n = 2 caveat; the single-chronological-split limitation was stated with the rolling-origin results as mitigation; the LLM arm description was updated for the completed retry. Every new number carries an HTML-comment source pointer. README.md's headline and status were updated for consistency.

## Step 10: remaining analytical gaps and paper readability

## Step 11: DeepLog diagnosis

- No saved checkpoint existed for either the main-run arm (which never saved one, computed validation loss, or did early stopping; it ran a fixed five epochs) or the Step 10 run (which deleted its checkpoint after writing each result to avoid committing model binaries). Both configurations were therefore retrained for the diagnosis on both HDFS_v1 splits, seed 0, keeping the checkpoints this time (`scripts/diagnose_deeplog.py`): lightweight (hidden 64, 100k windows, five fixed epochs, matching the main run) and full-strength (hidden 128, 1M windows, up to 15 epochs, patience 3). Training loss and validation loss tracking were added to the lightweight configuration for this comparison only; the frozen main-run results were not touched. Because LSTM and cuDNN training was not fully deterministic at this point (two reruns of the full-strength HDFS_v1/random configuration in Step 10 gave epoch-1 validation losses of 0.2127 and 0.2113), the diagnosis compares qualitative patterns and orders of magnitude across runs and says so wherever a cross-run number appears.
- Early-stopping validation set: `scripts/addendum_deeplog_fullstrength.py` was read line by line first. `val_normal = val[val["label"] == 0]` is what the early-stopping decision and the reported trajectory were built from, so early stopping used normal-only validation sessions. That candidate cause was ruled out by inspection, not by re-running.
- One training slowdown is noted for the record: epoch 5 of HDFS_v1/chrono/full-strength took about 948 seconds against a 130 to 140 second baseline everywhere else, reproducibly across three attempts, two of which ran past the job time limit before completing. `nvidia-smi` showed the GPU at 92 to 95% utilisation throughout and no orphaned process between attempts, so this reads as a transient environmental cause (thermal or OS activity) rather than a training bug. Training completed normally once past that epoch, with early stopping at epoch 8.
- Finding: all four diagnostic checkpoints show 97.5% to 99.2% of test sessions scoring exactly zero at top-9, including the lightweight configuration that matches the main run. State-dict hashes are identical before and after loading and after scoring for all four models, which rules out a loading or scoring-mutation bug. Mean NLL scoring restores sensible ranking for all four (AUROC 0.97 to 0.99 against top-9's 0.70 to 0.88). Conclusion: saturation, not a loading bug and not an unexplained real effect. Because the lightweight configuration's saturation rate (97.5% random, 98.5% chrono) clears the pre-set 80% threshold by a wide margin, the main-run deeplog cells have a defect and were corrected and re-run under the protocol's rule for bugs found after a verdict.
- Remediation: `results/full/HDFS_v1/{random,chrono}/deeplog/` and `results/full/BGL/{random,chrono}/deeplog/` (all five seeds) plus a snapshot of the pre-correction `summary.csv` were copied to `results/superseded/deeplog_v1/` before anything changed. `src/arms/deeplog.py` was rewritten: mean NLL is the primary score; the top-9 miss rate is kept as a secondary score (`secondary_topk9_*` fields in each cell's JSON) so the original heuristic stays inspectable; early stopping on normal-only validation loss (patience 3, up to 15 epochs) replaced the fixed five epochs. `src/run_all.py` got a one-line special case (`if arm_name == "deeplog": arm.fit(ctx, train, val)`) rather than a signature change for every arm. Validated on `--selftest` before touching `results/full/`. The old deeplog cells were deleted and only deeplog was re-run (20 cells) through `scripts/rerun_deeplog_corrected.py`, which reuses `run_cell()` unchanged; no other arm's cells were touched. Verdicts were recomputed into `results/full/VERDICTS_v2.md`; `VERDICTS.md` stays as the pre-registered record.

## Step 13: seeding

- `src/arms/deeplog.py`'s `fit()` now seeds `random`, `numpy`, `torch.manual_seed` and `torch.cuda.manual_seed_all` from the cell's seed and sets `torch.backends.cudnn.deterministic = True` and `benchmark = False` for the arm's training. No other arm needed this: iforest, ocsvm's subsample, pca and supervised_lgbm are seeded through sklearn and LightGBM's `random_state`, and semantic_knn's embedding model is frozen and deterministic at inference.
- Determinism confirmed with `scripts/check_deeplog_determinism.py`, which trains and scores deeplog twice in two separate Python processes (not two in-process calls, which could share warm cuDNN state) on the selftest HDFS_v1/random/seed0 split. Both runs produced identical AUROC (0.6207058823529412), AUPRC (0.19982735227823634), F1_val and F1_oracle. Result in `results/audit/deeplog_determinism_check.json`.
- The released deeplog cells were not re-run. This is a reproducibility fix rather than a correctness fix: the recorded scores are valid draws, and only future re-runs gain bit-reproducibility. Re-running 20 cells would cost compute for no expected change to any verdict, since the across-seed standard deviation already captures this size of run-to-run variation. The limitation is stated in `REPRODUCE.md` and the paper's Threats to validity, quoting the across-seed AUPRC standard deviation range (0.0055 to 0.0903 across the four dataset and split combinations) so anyone re-running knows what tolerance to expect.
